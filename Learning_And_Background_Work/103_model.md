**Blog Series:** *Evolving Cline: Building the Universal Code Orchestrator Workbench*

**Part 3: Simple Sequences - The Basic Workflow Orchestrator**

**Welcome Back, Workbench Engineers!**

In Part 1, we refactored Cline's core execution logic into a reusable `AgentInstance` capable of performing a single agentic step. In Part 2, we designed the `AgentBlueprint` – the template defining the characteristics (prompt, tools, model) of specialized agents. We now have the actors (`AgentInstance`) and their scripts (`AgentBlueprint`). The next crucial component is the **director**: the entity that manages the performance, tells the actors when to take the stage, and passes information between scenes.

This post focuses on designing and implementing the initial version of this director: the **Workflow Orchestrator**. We'll start simple, building an orchestrator capable of executing a predefined, *linear sequence* of agent steps. This foundational piece will manage the lifecycle of a workflow instance, handle the flow of information between agent steps, and establish basic state management and persistence. We'll follow our design discussion format with **A (Ideator)**, **B (Critic)**, **C (Implementer)**, and **D (Refiner)**.

---

**Session Start: From Blueprint to Action Sequence**

**Coder A (Ideator):** We have `AgentInstance` (executes a single step) and `AgentBlueprint` (defines an agent type). Now we need the system to run a *sequence* of these based on a user's request. Let's define a simple `WorkflowDefinition` containing just an ordered list of steps, where each step specifies which `AgentBlueprint` to use. I propose creating a new `WorkflowOrchestrator` service (`src/services/workbench/WorkflowOrchestrator.ts`). Its initial job will be to take a `WorkflowDefinition` and an initial input (like the user's task prompt), then instantiate and execute the `AgentInstance` for each step *sequentially*, feeding the primary output of one step as the main input to the next.

**Coder B (Critic):** "Feeding the output" is still the core challenge here. What exactly constitutes the "output" of an `AgentInstance` step that should become the "input" for the next? Is it just the final assistant text message? The structured result of a tool call if one was made? What about the full conversation history generated *within* that step? If Agent 1 reads a file and Agent 2 needs that file content, how does Agent 2 get it if only Agent 1's final text message is passed?

**Coder A (Ideator):** Good point. Simply passing the last text block is insufficient. The `AgentInstance.executeStep` needs to return a structured result. Let's refine the return type (building on Part 1's idea):
```typescript
interface AgentStepResult {
  success: boolean;
  outputContent: UserContent; // Formatted content suitable as the *primary user input* for the next step.
  // Example: If step was `read_file`, outputContent could be [{ type: 'text', text: '<file_content path=...>[content]</file_content>' }].
  // If step was just text generation, outputContent could be [{ type: 'text', text: 'Generated text...' }].
  finalAssistantMessageBlocks: AssistantMessageContent[]; // Full structured blocks (text, tool_use) generated by the assistant in this step.
  finalToolResult?: ToolResponse; // The actual result returned by the tool, if one was executed.
  error?: string;
  // apiMetrics, duration, etc. later
}
```
The Orchestrator will manage the *overall* `apiConversationHistory` for the entire workflow instance. For step N:
1. It takes the `outputContent` from step N-1's `AgentStepResult`.
2. It formats this `outputContent` into a *new* `user` message.
3. It appends this `user` message to the `instance.conversationHistory`.
4. It passes the *updated* `instance.conversationHistory` to `AgentInstance.executeStep` for step N.
5. After step N completes, it gets the `finalAssistantMessageBlocks` from the `AgentStepResult` and formats/appends these as an `assistant` message to the `instance.conversationHistory`.
This ensures the full conversation context builds up, while the `outputContent` provides the immediate trigger/input for the next step.

**Coder B (Critic):** Okay, that clarifies the data flow. The Orchestrator acts like the user in a normal Cline session, appending the assistant's full response and the *next* input (derived from the previous step's output) to the history. What about error handling and persistence? If step N fails, does the whole workflow just stop? What if VS Code closes mid-workflow?

**Coder A (Ideator):** For V1, yes, halt on first error. We'll add conditional branching later (Part 31). Persistence is critical. We need a `WorkflowInstance` state object:
```typescript
interface WorkflowInstance {
  instanceId: string;
  definitionId: string;
  status: 'running' | 'succeeded' | 'failed';
  currentStepIndex: number;
  startTime: number;
  endTime?: number;
  // The *complete* history for this instance
  conversationHistory: Anthropic.MessageParam[];
  // Store results of each step
  stepResults: AgentStepResult[];
  // Add scratchpad later
  error?: string; // Store error message if status is 'failed'
}
```
The `WorkflowOrchestrator` must save this entire `WorkflowInstance` object to disk (e.g., `globalStorage/tasks/workflow_{instanceId}/instance_state.json`) *after each step completes*. On VS Code startup, the Orchestrator should scan for instances left in the 'running' state and mark them as 'failed' due to the interruption. Full resumption is a future enhancement.

**Coder B (Critic):** Persisting the full `conversationHistory` and `stepResults` after every step could become storage-heavy, especially if `outputContent` or `finalAssistantMessageBlocks` contain large data (like full file contents). We need to be mindful of this, perhaps implementing truncation or referencing strategies later. But for V1, persisting the full state ensures durability. Halting on first error is simple to start with.

**(A and B agree on sequential execution, the `AgentStepResult` structure, the Orchestrator managing history and persistence per step, and halting on first error.)**

**Implementation Details (Coder C & D)**

**(C outlines the initial implementation, D suggests refinements)**

**Coder C (Implementer):**
1.  **Define Schemas (`src/shared/workbench/types.ts`):**
    *   Implement `WorkflowDefinition` (as defined by Coder A: `id`, `description`, `steps: { stepId, blueprintId, initialPromptModifier? }[]`).
    *   Implement `AgentStepResult` (as defined by Coder A). Ensure sub-types like `UserContent` (`ContentBlockParam[]`), `AssistantMessageContent[]`, `ToolResponse` are correctly imported/defined and JSON-serializable.
    *   Implement `WorkflowInstance` state object (as defined by Coder A).
2.  **`WorkflowOrchestrator` Service (`src/services/workbench/WorkflowOrchestrator.ts`):**
    *   **Dependencies:** Inject `BlueprintService` (from Part 2), `AgentInstance` factory (or its dependencies like `McpHub`, `Controller` for `ask`), storage path function, `LoggingService`.
    *   **State:** Use an in-memory `Map<instanceId, WorkflowInstance>` for active workflows.
    *   **`async startWorkflow(definitionId: string, initialInputText: string): Promise<string>`:**
        *   Loads the `WorkflowDefinition`. Handles errors if not found.
        *   Generates a unique `instanceId`.
        *   Creates the initial `WorkflowInstance` state: `status: 'running'`, `currentStepIndex: 0`, `startTime`, `conversationHistory: [{ role: 'user', content: [{ type: 'text', text: initialInputText }] }]`, `stepResults: []`.
        *   Persists this initial state asynchronously via `_saveWorkflowInstance`.
        *   Adds the instance to the `activeInstances` map.
        *   Triggers the first step: `this._executeWorkflowStep(instanceId, 0)`. **Do not `await` this call**; let it run in the background.
        *   Returns the `instanceId`.
    *   **`async _executeWorkflowStep(instanceId: string, stepIndex: number): Promise<void>`:** (This is the core recursive/looping logic, likely called internally)
        *   Retrieve `instance` state from `activeInstances`. If not found or status isn't 'running', log and return.
        *   Get the `stepDefinition = instance.definition.steps[stepIndex]`. Handle index out of bounds (means workflow succeeded previously).
        *   Load the `blueprint = await blueprintService.getBlueprint(stepDefinition.blueprintId)`. Handle blueprint not found error.
        *   Determine the input for this step:
            *   If `stepIndex === 0`, use the `initialInputText` (perhaps formatted).
            *   If `stepIndex > 0`, get `previousResult = instance.stepResults[stepIndex - 1]`. Format `previousResult.outputContent` into a `UserContent` array.
        *   Construct the *full prompt* for the `AgentInstance` (combining blueprint prompt and step-specific modifiers/input).
        *   Construct the history segment to pass (likely the full `instance.conversationHistory` up to this point).
        *   Log `AgentStepStartEvent`.
        *   Instantiate `AgentInstance`. Provide necessary dependencies and an `approveToolCallback` that routes back to the `Controller`'s `ask` mechanism.
        *   `const stepResult = await agentInstance.executeStep(...)` (wrap in `try...catch` for internal agent errors).
        *   Log `AgentStepEndEvent`.
        *   **Update `WorkflowInstance` State:**
            *   Append the *new user message* (containing `previousResult.outputContent`) AND the *assistant response* (`stepResult.finalAssistantMessageBlocks`, formatted) to `instance.conversationHistory`.
            *   Add `stepResult` to `instance.stepResults`.
            *   Check `stepResult.success`.
            *   If `!success`: Set `status = 'failed'`, `error = stepResult.error`, `endTime`. Persist, notify UI, remove from `activeInstances`. **Stop.**
            *   If `success` and `stepIndex === instance.definition.steps.length - 1` (last step): Set `status = 'succeeded'`, `endTime`. Persist, notify UI, remove from `activeInstances`. **Stop.**
            *   If `success` and not last step: Increment `currentStepIndex`. Persist state (`_saveWorkflowInstance`). Notify UI. **Recursively call `_executeWorkflowStep(instanceId, stepIndex + 1)`**.
    *   **`async _saveWorkflowInstance(instance: WorkflowInstance): Promise<void>`:** Writes the instance state to its dedicated file (`globalStorage/tasks/workflow_{instanceId}/instance_state.json`). Handles errors.
    *   **`async loadAndMarkFailedInstances(): Promise<void>`:** (Called on extension startup) Scans the task storage directory for `workflow_*` folders containing `instance_state.json` with `status: 'running'`. Loads them, updates status to 'failed', saves them back, and potentially populates a list for the UI to show interrupted workflows.
3.  **Controller Integration:** Add a mechanism (e.g., a new command or triggered via UI) to call `WorkflowOrchestrator.startWorkflow`. The Controller needs to pass necessary dependencies (like itself for the `ask` callback) to the orchestrator.
4.  **UI (Instance Monitor V1):** Implement the basic list view showing `instanceId`, `workflowId`, `status`, `startTime`. Allow clicking to perhaps show the raw `instance_state.json` content initially.

**Coder D (Refiner):**
*   **Refine C:**
    *   **Input/Output Typing:** Be very precise about the `UserContent` type passed between steps. Using the structured `ContentBlockParam[]` type is good. Ensure the formatting logic (converting `AgentStepResult.outputContent` to the next step's `UserContent`) is robust.
    *   **State Persistence Robustness:** Saving the *entire* `WorkflowInstance` (including full history) after every step might be slow for large histories/results. Consider optimizing later by saving only diffs or using a more efficient storage format if needed, but start with full saves for simplicity and durability. Ensure file writes are atomic (write to temp file, then rename) to prevent corruption.
    *   **Error Propagation:** When `_executeWorkflowStep` catches an error from `agentInstance.executeStep`, ensure this error is properly stored in the `WorkflowInstance.error` field and the status set to 'failed'.
    *   **Circular Dependencies:** Be careful when passing dependencies. `WorkflowOrchestrator` needs access to services, and `AgentInstance` needs access to the orchestrator (or Controller) for things like tool approval. Manage dependencies cleanly using dependency injection or well-defined interfaces. Avoid direct circular class dependencies.
    *   **Initial UI Feedback:** When `startWorkflow` is called, immediately notify the UI that the workflow has started (e.g., add a placeholder to the Instance Monitor) before the first step even begins execution in the background.

**Conclusion: Conducting the First Movement**

The `WorkflowOrchestrator` is the conductor bringing our specialized `AgentInstance` actors together. By implementing a service that executes predefined linear sequences, manages the flow of information (`outputContent` -> next input), maintains the overall conversation context (`conversationHistory`), and diligently persists the state of each running workflow instance after every step, we build the fundamental engine of the Cline Workbench. This initial version, while simple (sequential, halt-on-error), provides the critical foundation upon which conditional logic, parallelism, richer communication, and advanced monitoring will be layered in subsequent development phases.
